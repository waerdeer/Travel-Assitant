# 演示与学习路线

## 先跑通一段完整故事

1. 开启新旅程，输入“我想去杭州玩两天，喜欢博物馆，人均预算1000元”。观察系统先问日期，工具调用数为 0。
2. 给一个未来出发日期。已明确“两天”时，系统会计算返程日。检索后先比较住宿与餐饮候选，选一家住宿及 1–3 家餐厅，或者交给 Agent 决定；确认后才进入规划。也可先刷新，展示等待选择的状态如何恢复。
3. 查看每日计划、费用估算、来源链接与待核实事项；切换完整计划并导出 Markdown。
4. 输入“每天最多两个景点，轻松一点”，对比新旧节奏与证据复用情况。
5. 输入“酒店换成附近的经济型酒店，其他日程别动”，重新选择住宿候选后，确认每天活动原样保留，只调整住宿。
6. 刷新页面，再从历史打开会话，继续修改。解释消息表、行程表和轮次快照的职责。

不要把费用说成实时价格，也不要把酒店检索说成已预订。模型服务与地图网络不稳定时，展示真实错误和恢复方式；面试前提前运行一次真实冒烟脚本。

## 代码阅读顺序

1. `schemas/planning.py`：先理解模型和程序之间的契约。
2. `graph/workflow.py`：跟着主图走一遍分支和循环。
3. `graph/pipeline.py`：看语义决策、完整规划与酒店局部修改。
4. `graph/choices.py`：看人类决策边界、候选 token、选择校验及恢复为何跳过需求理解。
5. `graph/research.py`、`geography.py`：看数据来源、缓存、重试和预算如何落地。
6. `graph/validation.py`：把每个约束对应到实际错误案例。
7. `agents/orchestrator.py`、`services/persistence.py`：看同会话串行化、重启恢复与原子保存。
8. `tests/test_closed_loop.py`、`test_geography_and_api.py`、`test_human_choices.py`：用测试证明上述行为。

## 可以这样介绍项目

“我做的是一个受约束的旅行规划 Agent。模型负责需求理解、搜索策略和行程安排，程序负责工具契约、执行预算和验收。行程以结构化数据引用真实地点；校验失败会把错误代码反馈给规划器，必要时补充检索。达到上限仍失败就不交付为已完成计划。实际测试发现过同城跨区绕行，我进一步补了 POI 详情坐标查询和地理校验，并解决了详情接口的 QPS 限制。”

这段描述需要你能展开讲每个设计，不能只背技术名词。

## 面试追问与回答要点

| 追问 | 应解释的内容 |
| --- | --- |
| 为什么不用一个大 Prompt？ | Prompt 无法可靠计算所有约束；独立状态、证据和验收能暴露错误并支持定向修正。 |
| 为什么没有堆多个自治 Agent？ | 任务角色不等于独立自治实体。当前主要复杂性在证据与约束，过度拆分会增加调用和状态协调成本。 |
| 这是不是普通工作流？ | 图拓扑有界，语义决策、搜索主题、证据刷新和计划由模型决定；验收后的反馈形成规划循环。应称为混合工作流中的受约束规划 Agent，不夸大开放式自治能力。 |
| 幻觉解决了吗？ | 主行程只能引用检索证据；说明文字与费用仍由模型生成，未全面事实核查，因此只是缩小幻觉空间。 |
| 地点真实，为什么路线仍会错？ | 市级搜索覆盖远郊；真实地点不等于相邻地点。用真实失败案例解释坐标补全与距离约束。 |
| 如果模型一直改不好？ | 有规划修正次数、工具调用总量和整轮超时三道上限；返回未满足的具体约束，保留上个有效版本。 |
| 如何保证只换酒店？ | 更小的输出契约加程序合并，不允许该分支生成新的每日活动。 |
| 为什么在这里加入人类选择？ | 住宿和口味是主观偏好，值得在规划前集中确认一次；机械计算和工具调用不逐次打断。选择会成为规划与校验约束。 |
| 暂停期间程序在运行吗？ | 本轮返回并持久化待选择状态，不保持活跃协程。下一请求校验 token 和 ID 后直接恢复到规划；这是业务暂停，不是任意节点断点续跑。 |
| 怎样防止重复或过期选择？ | 会话锁内先检查当前 token、候选归属和时效；成功后清除待选择状态。重复提交不会多调用一次模型。 |
| 为什么需要结构化数据和 Markdown 两份？ | JSON 用于校验、修改与卡片展示；Markdown 从通过校验的数据确定性渲染，供阅读与导出。 |
| MemorySaver 能持久化吗？ | 内存不能跨进程。当前保存轮次 JSON 快照到 SQLite，能恢复下一轮，但不支持中间节点续跑。 |
| 如何评价好坏？ | 分开行为回归、约束检测评估、真实生成成功率与延迟；不把固定测试的满分当作开放任务准确率。 |
| 怎么优化成本？ | 简单澄清只调用需求理解；证据复用；只对选中地点查详情；酒店修改使用小契约；所有物理调用都计数。 |

## 下一轮可深入的方向

- 将直线距离筛查升级为真实步行／公共交通路径与耗时校验。
- 加入营业时间、预约条件、价格与房态来源，减少只能提示“待核实”的部分。
- 用固定真实需求集比较首次通过率、修正后通过率、工具失败率和延迟分布；增加多次采样。
- 从轮次快照升级到持久化 LangGraph 中间检查点，再考虑多 worker、请求幂等与用户隔离。

这些是后续方向，不属于当前已经完成的能力。

## 抵离时间的对抗演示

输入：“2026年11月1日到3日去杭州，1日19点才到，当天只入住休息，3日10点离开，2日看博物馆和西湖。”随后：“返程改到3日12点，其他不变。”

展示首末日留白、接驳假设和中间游玩日，再说明为什么不能只依赖提示词：旧领域模型强制每天有景点，同时自由文本里的抵离时刻不参与校验，会把合理空日拒绝、错误白天活动放行。现在 Requirements 明确时刻/缓冲/rest_dates，程序计算 daily_schedule，并独立检查草案和最终活动；模型不能靠声明空日豁免普通日或全程必去。

取消要求也要有明确语义。以“不要取消返程时间限制”“取消返程时间限制吗”“取消返程限制，但请保持原时间”为反例，说明原文引用只用于定位，完整分句和冲突检查才决定是否释放。无法确定时保留并澄清。这个保护是保守规则，不能宣称覆盖任意中文表达。

实测两轮74.382秒和38.635秒，首末日无景点、返程修改保留首日要求。样本见 `reviews/availability-live-2026-10-25.json`；部分地图详情超时，距离未完全核验。接驳60/90分钟是排程假设，不能声称已经接入机场/车站真实交通或完成预约时刻校验。
