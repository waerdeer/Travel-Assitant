# 按需浏览食宿：独立验收与北京截图根因

本轮用户明确要求：完成行程后，在住宿和各目的地提供“浏览酒店”“浏览特色美食”；点击才展示，联动另一聊天修改并验证。本文是验收约定，尚非通过报告。

## 截图能证明的现象与代码根因

截图显示北京多片区路线草案，校验失败后要求重新选择食宿，并未证明正式行程已经保存；不能仅凭截图断言哪一家店导致失败。

已以 SQLite `mode=ro` 只读核对原北京 2026-10-29 至 11-01 会话：状态 `awaiting_choice`、无 `accepted_plan`，校验 trace 有 10-31 两次 `transfer_buffer`，11-01 一次 42.6 km `long_transfer`、一次 37.0 km `distant_hotel`。这说明既有时间留白问题，也有长距离门槛问题；不能仅降低酒店门槛就宣布整个案例修好。未修改或继续该用户会话。

独立合成反例 `/tmp/travel-on-demand-review/reproduce_spatial.py` 已复现：给 `review_options` 仅传入景点到景点的 44.2 km `long_transfer`，它仍返回“住宿或餐饮与景点距离过远”的餐厅选择面板。此反例证明错误分流，不声称复刻用户原始模型输出。

已核实旧实现存在：

- `validation.py` 的 `long_transfer` 表示任何相邻地点直线距离超过 30 km，可能是景点到景点。
- `choices.review_options` 把 `long_transfer` 统一解释为需要重新选择餐饮；`research.collect_evidence` 同样转为餐厅周边检索。因此真实原因可能是景点顺序，却让游客改餐厅，不能消除冲突。
- `distant_hotel` 对同一家酒店到每一天首末景点使用 30 km 一刀切错误门槛。多片区旅游未必不成立，缺少交通方式和导航结果时，不能把直线距离直接等同不可行。
- 校验器只要检索到餐厅，就要求每天具体餐厅；只要检索到酒店，就要求多日行程指定酒店。它把“有候选”当成“必须使用”，与用户按需浏览目标冲突。

## 距离判断的产品边界

1. 保留引用真实性、停业、跨城错误、时间重叠、必去/排除/已订地点、预算与节奏等硬约束。已订酒店不能为了通过校验静默换掉。
2. 单凭酒店到景点直线超过 30 km，不足以证明路线不可能。应显示具体日期、酒店及景点、直线距离和未核实交通提示；明确是较长通勤风险，不能声称导航时间已验证。
3. 同日景点之间长距离需要结合时间留白判断。不能把长距离错误全部改成 warning 后放行紧接的活动；短时间长距离应要求重排或澄清交通。距离估算的时间门槛只是保守排程启发式，不是导航承诺。
4. 修复对象必须对应冲突：景点到景点修活动/顺序，涉及餐厅才修餐厅，酒店通勤提示不能统一变成餐厅重选。无进展修复必须有限停止并解释具体原因。
5. 默认不确定酒店、餐厅也能完成行程；保留用餐与住宿预算及休息留白。显式用户锚点仍必须检索、安排和保护。

## 必须验证的行为

| 编号 | 场景 | 通过条件 |
|---|---|---|
| B01 | 默认多日规划 | 不停在 awaiting_choice；无选店操作也能取得完整行程 |
| B02 | 有酒店/餐厅检索事实但未选店 | 候选存在不强制填入计划；自由用餐/住宿建议表达清楚 |
| B03 | 住宿与美食入口 | 每日合理住宿位置、不同活动地点提供对应按钮；不是同一个全城搜索结果重复铺满 |
| B04 | 点击浏览 | 根据正式行程日期及活动地点请求；不启动整轮模型规划、不锁定候选 |
| B05 | 只读性 | 浏览前后 accepted_plan、Trip、会话消息与 checkpoint 不被候选覆盖 |
| B06 | 版本绑定 | 旧版本/错误日期/不在计划中的地点不允许拿来检索；不任意接受客户端坐标 |
| B07 | 客户端竞态 | 切会话/重规划/删除/关闭后，旧请求结果不能出现在新计划；快速切按钮无串卡 |
| B08 | 空结果与服务异常 | 可理解的空状态/失败/重试；原行程继续可读，按钮恢复，不无限加载 |
| B09 | 图片 | 仅使用来源实际提供并匹配地点的图片；有来源，缺失与加载失败有替代显示，不阻塞文字 |
| B10 | 图片输入异常 | 异常结构、无效协议/空链接不使后端或页面崩溃；不把图标/其他门店照冒充实景 |
| B11 | 候选准确性 | 停业、错误城市、过期事实不展示为当前可用候选；距离/价格标签不夸大证据 |
| B12 | 北京景点跨片区 | 景点之间冲突不再要求改餐厅；足够留白与不足留白分别检查 |
| B13 | 远距离已订酒店 | 保留用户锚点；给出具体通勤风险，必要时问交通/范围，不能擅自换店 |
| B14 | 浏览后继续改行程 | 浏览结果不成为隐含硬约束；修改失败保留上一正式版本 |
| B15 | 单日、最后一天、历史计划 | 不强制一日游住宿；返程日不默认当晚必须住宿；旧 schema 可读且合理降级 |
| B16 | 兼容与流式 | 显式 guided 旧接口可兼容；默认界面不再出现强制选择；已有真实进度仍有效 |
| B17 | 实际页面验证 | 默认规划→完成→点酒店/美食→展示结果/图片降级→换地点→刷新/改行程；必须有实际 API 和浏览器证据 |

## 交付证据要求

自动化应覆盖生产逻辑与数据库隔离，不只对新按钮做快照或复制实现断言。真实模型/地图单样本只能说明该样本，不代表覆盖任意中文需求或所有地点都有图片。

独立验收至少复核：关键代码路径、针对性反例、后端正式回归、前端 lint/build、隔离服务 API 与实际按钮交互。图片如只能验证占位和失败降级，须如实写明，不能宣称实景图片链路已成功。
