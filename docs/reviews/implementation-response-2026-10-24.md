## 第二轮 R2-1／R2-2 的修复响应（待第三轮独立复验）

- 状态字段与名称复用同一组明确负面状态，“暂停营业、暂不营业、已关闭、已停业”等中文字段均被识别；仍不猜测未知数字枚举或模糊文本。
- 详情解析先核对 POI ID，再同时处理坐标及明确不可用信号。带或不带坐标的关闭信息均保存为证据中的 canonical business_status=closed，并记录详情名称、来源与时间；保留原 evidence ID 和原名称，不用删除证据消除约束。错误或缺失 ID 不能污染原条目。
- 检查所选约束时会读取更新后的证据。自动模式虽未保留特定所选 ID，如果来源已经确认某一必要类别全部不可用且无有效替代，也不能退化成普通“数据缺失”警告后宣称完成；有有效替代时仍允许自动修复。
- 新增12项中文字段参数测试、完整图字段拒绝，以及酒店／餐厅／景点的详情关闭（有／无坐标）、错误或缺失 ID、正常详情、accepted_plan保护、自动全失效阻断／有效替代完成等测试。既有“无酒店来源且未指定酒店时允许警告”的契约仍保留。
- 后端最终本地测试数量见第三轮报告；前端业务代码与上一轮相同。第三轮期间再次冻结业务代码，独立方可自行复验和质疑。

## 第三轮 R3-1 的修复响应（待第四轮复验）

- `fresh_evidence` 增加事实存储模式：研究节点和需求复用保存当前有效的负面事实；可选候选与规划输入仍排除不可用地点。某类别仅有负面事实时，仍会尝试搜索有效替代，不把负面事实当作检索已齐全。
- 显式换候选／仅换酒店时也保留有效负面事实。按同 ID 合并证据时，新返回缺少状态字段不能抹掉已知关闭；只有来源时间更新且明确给出营业状态，或有更新的关闭事实，才更新状态。没有新状态时保持旧负面事实时间，不靠不断检索无限延长旧信号；城市变化／新旅行与原TTL规则仍有效。
- 正式组合回归覆盖酒店关闭+餐厅过远+附近餐厅成功+恢复选择+缺酒店：保留关闭事实、阻断新正式版、accepted_plan不变。另覆盖三类地点负面事实保留、显式刷新、同ID未知／旧营业／新营业状态更新，以及“建设中路”正常地址名负例。
- 第四轮业务代码冻结；请独立方重放组合反例并尝试有效酒店替代、来源时间和状态冲突等边界。

## 第四轮 R4-1／R4-2 的修复响应（待第五轮复验）

- 新增统一 `fact_time`，关闭事实以有效的详情来源时间和原检索时间中的较新时间判断自身TTL；不改动原始地点检索时间，不声称原位置／价格等其他信息被一并刷新。缺状态更新不续期负面事实，真正过期、异城及未来时间仍按有效性过滤。
- `merge_evidence` 两个方向统一比较有效事实时间。较旧记录不再依赖输入顺序覆盖新状态；等时刻出现明确关闭／营业冲突时保守保留关闭。
