# 产品迭代第一批：最小交付与独立验收标准

日期：2026-10-24。依据：`docs/product-review-2026-10-24.md`、补充方案 `docs/product-flow-v2.md` 和当前生产代码。本文是实施前标准，不是已实施或已验收结论；不修改业务代码。

## 1. 本批交付目标与边界

**必须实现：用户在选择具体酒店／餐厅之前，先看到有证据的每日路线草案；食宿候选结合草案提供，用户可直接交给系统继续；普通喜好不会自动变成指定门店的硬约束；草案、等待和正式版有清晰边界。**

不能仅把完整结果换成打字动画，也不能在已经检索完全部食宿后把最终行程复制一遍，称为“路线优先”。必须改变至少默认新规划路径的依赖与交付顺序。

本批定位为上一版方案的A批，允许后续逐步完善，不要求一次完成所有B／C批能力。

| 本批必须 | 后续，不作为本批阻断项 |
| --- | --- |
| 有结构和证据的路线草案，在默认食宿选择前且最终结果前可见 | 完整逐字输出、所有单日内容增量解析 |
| 普通新规划先形成主要活动骨架，再检索／比较相关食宿 | 每顿饭独立的通用决策引擎及任意对象编辑 |
| guided保留必要决策，automatic可无具体选店操作完成 | 完整自由用餐／休息日／多住宿点领域重构 |
| 偏好与明确指定有可执行的语义区别 | 复杂偏好权重、用户画像、多人投票 |
| 明确已订酒店／必去餐厅的可用证据得到保护或冲突解释 | 接入真实预订、库存、房态与订单管理 |
| 草案与pending在已完成的等待轮次持久化，并可恢复 | 执行中任意节点断点恢复、后台任务系统 |
| 食宿卡片有与路线的关系说明，沿用可核实的事实边界 | POI照片、地图联动、真实导航、价格聚合 |
| 沿用前五轮通过的事实、时效、选择与正式版不变量 | 多城市、北疆环线、公开多租户上线 |

图片对最终体验有价值，但本批不让供应商图片接入成为流程改进的前置依赖。若实施方自愿接入，仍须准确绑定POI、来源明确、不阻塞草案；假实景不能填充真实门店卡片。

## 2. 最小关键交互

### 默认新规划

1. 先理解日期、目的地、节奏、已有锚点；缺必要信息或超范围则澄清。
2. 检索游览地点／必要的用户指定锚点证据，形成每日主要活动草案。
3. 通过流事件立即展示草案。界面明确写“路线草案／待完善食宿”，能看见日期、每日主题与主要活动及其证据来源。
4. 再按草案的活动区域提出住宿／餐饮候选，说明为何与这条路线有关。不能只显示“检索方向”代替推荐依据。
5. 用户可选择具体候选或交给系统。guided可以保留一次集中食宿比较，不要求本批每顿饭独立暂停；但此时已有路线可参考，住宿和餐饮也不能都被描述成必须预订。
6. 恢复后复用草案与已有证据完善行程，检查全程约束，再发布正式版本；冲突只在必要取舍时回到用户。

草案不是新加强制审批页。用户不想逐项指定时，有明确的一键继续路径；automatic请求不因默认选择节点阻断。

### 已有锚点例外

用户明确“已经订了某酒店”或“专程吃某家餐厅”时，相关证据应先于或参与骨架形成。路线优先不能变成忽略用户锚点。未定位到指定地点、地点不可用或与范围冲突时先说明，不发明ID或无声替换。

“喜欢杭帮菜／酒店安静些／对某家店感兴趣”是软偏好；“一定要去／已经订好／就选这家并据此继续”才产生明确约束。候选本身不是用户偏好，更不是预订。

## 3. 最小状态与接口契约

命名可由实施方调整，以下是必须可观察的语义，不要求建立庞大的通用系统。

### 路线草案

至少包含草案ID或版本、城市、日期覆盖、每日主题／主要活动证据引用、路线／区域假设、未完成项与检查范围。草案的主要活动只使用同城、当前可用且有证据的地点；时空未知应明确标记，不宣称已完成导航或营业核验。

本批不要求草案提前具备完整时刻表、酒店、每顿餐厅与总费用。为满足现有Itinerary而塞假酒店、餐厅或零费用不可接受。优先使用独立草案schema；若复用部分类型，也必须有分开的校验与交付边界。

### 需求与选择语义

- 软偏好可继续使用preferences，但必须不会自动写入限定可选池的selected_options。
- 明确酒店／餐厅要求需要能保存、恢复并检查。可以增加最小的结构化地点约束字段，或在现有需求与selected_options之间建立明确契约；仅靠提示词说“尽量保留”不足以保护明确锁定。
- 用户手动确认候选的含义应显示清楚：例如“采用该酒店”“按这些餐厅继续”。不能把收藏当硬约束，也不能把本批仍沿用的全程餐厅池伪装成某一顿饭的局部指定。
- pending至少关联当前草案版本／需求上下文。token可继续作为客户端提交的最小字段，但服务端必须检测旧草案选择不能作用到新方案；不强制要求老客户端立刻新增必填版本字段。

### 草案／正式版／生命周期

- draft独立于accepted_plan、final_plan_md和正式Trip；任何草案显示事件都不能直接覆盖原正式版。
- awaiting_choice轮次完成时，草案、对应候选及恢复所需约束一起原子保存。刷新／新orchestrator实例能重建相同上下文。
- 对尚未完成的执行轮次，继续如实保留现有断连取消边界。本批不要求把中间草案都即时落盘，也不能声称已经支持任意断点恢复。
- 改城市、日期或重新形成草案时，应清除／替换不再适用的草案和pending，避免跨会话串线。失败修改保留旧正式版，但不得把旧正式版标成此次新草案已完成。

### HTTP与流式输出

- `/chat_plan` 与 `/chat_plan/stream` 共用同一业务语义。新响应可增加draft，正式plan字段继续只放正式内容。
- SSE必须在最终result前传递可渲染草案对象与对应证据；只发“正在规划”不通过。可以扩展现有progress payload，也可以新增事件，不强制特定名称。
- 节点／分支事件准确表达正在执行的动作；若新图增加草案节点，不应继续依靠旧静态映射把“规划草案”误标成“正在校验”。
- 现有历史详情当前只返回pending_choice和last_run，需要扩展以恢复草案或提供等价读取入口。非流式客户端和无draft的历史记录仍可读取。
- 旧版pending的迁移／失效策略必须显式，不得让新恢复逻辑绕过旧范围策略检查或接受重复token。

## 4. 会受影响的现有代码与规则

| 位置 | 预期影响 |
| --- | --- |
| `graph/workflow.py` | 固定research→review_options→plan需要拆分／重排；选择恢复应转到草案完善而不是丢掉草案重头开始 |
| `graph/research.py`、`RequestDecision` | 游览检索与普通食宿检索按依赖分阶段；食宿按骨架位置生成查询，保留事实合并、负面状态、有效时间和共享预算 |
| `schemas/planning.py`、`graph/state.py` | 草案契约、版本、明确酒店／餐厅要求及恢复状态；不能把草案当最终Itinerary强行验收 |
| `graph/choices.py` | pending关联草案，手选与自动语义清楚；五轮已验证的有效性、token、版本、指纹检查仍生效 |
| `graph/pipeline.py`、`validation.py` | 草案与完整行程分开检查；明确地点约束独立验收；完整行程仍检查预算、时间、地点引用、必去与排除等 |
| `services/persistence.py`、`api/history.py`、历史schema | 等待轮次恢复draft；草案不能触发正式Trip upsert；旧记录兼容 |

| `Frontend/src/api.ts`、`types.ts`、`App.tsx` | 实际消费草案事件，显示／恢复／替换草案，正式版单独保存，reset和切换历史清理对应状态 |
| `ChoicePanel.tsx`、`TravelPlan.tsx`、`AgentInspector.tsx` | 先草案后候选；草案标签与无正式绿勾；新节点正确展示；食宿卡片说明路线关系 |

现有“每天必须有餐厅、多日需酒店、完整预算”等规则继续约束完整行程，不能拿来阻止草案先展示。自由用餐／不推荐住宿等新交付语义若未在本批实现，必须如实限定，而非通过删除校验偷渡。

## 5. 十二个必须验证的验收场景

测试输入中的日期可使用固定未来日期或时钟fixture；外部模型／地图以确定性替身检查行为，再用少量真实对话验证理解，不把两者混成成功率。

| 编号 | 触发与操作 | 必须观察到的结果 |
| --- | --- | --- |
| A01 首次路线价值 | 完整的单城两天需求，未指定食宿，默认guided | 在任何具体食宿选择之前看到覆盖两天、有合法主要活动引用的路线草案；流中draft早于result。普通食宿候选检索依据草案，不仍是初始全量食宿检索后才补一张草案 |
| A02 不想选具体店 | 同需求，automatic；或在草案后的选择处交给系统 | 无手选具体门店也可继续至可用结果；不因新草案再要求点击一次确认；不把自动建议说成已预订 |
| A03 guided上下文 | 草案后显示食宿比较，用户选合法候选继续 | 同屏或可直接查看相关路线，卡片有来源可支撑的区域关系说明；恢复沿用草案／约束，不重复已完成的初始理解和全量游览搜索；最终使用所确认内容或解释不可行 |
| A04 软偏好 | “喜欢本地菜，住得安静一点；某店看起来不错但不用非去不可” | 偏好进入理解／排序，不自动形成全程指定店池或锁定该店；系统可在其他合法证据中选。优先用结构化fixture证明，再补真实理解样本 |
| A05 明确住宿锚点 | “已经订了酒店H，别换酒店”；提供可用的H证据 | H参与骨架／后续规划，不再要求用户重新选酒店；修改餐饮或节奏不改H。无法定位／不可用时明确处理，不静默换店或虚构引用 |
| A06 明确餐厅锚点 | “一定要去餐厅R／已预约R”；可用R证据 | R作为可验证的明确约束被保留；若本批支持预约时刻则检查时刻，否则明确能力边界，不伪装已满足。另提供模型故意遗漏R的反例，不能仅靠提示词通过 |
| A07 草案真假边界 | 景点检索有结果但食宿还未检索；另给无景点证据、同城远距离及缺坐标变体 | 第一种可先出草案且标未完成；无证据不能伪造具体路线；已知远距离应提示／修正，缺坐标明确未知，不宣称顺路已核验；所有变体均不能给草案正式校验绿勾 |
| A08 失败保护 | 已有accepted_plan，修改需求后生成草案，再注入模型失败／校验失败／停止 | 原正式版不变；草案与失败状态不混作正式plan，导出仍只导有效正式版；停止后不继续发布此轮对象 |
| A09 等待后恢复 | 草案＋pending进入awaiting_choice；刷新前端／新orchestrator读取相同临时SQLite，再选候选 | 草案版本、证据、约束和候选一致恢复，正确继续；不是只剩选店面板或退回旧正式版。无draft老会话仍能打开 |
| A10 旧决策与串线 | 草案形成后改变日期／城市或换新候选；提交旧token；前端切换会话／新建 | 旧决策不能修改新草案，重复提交零额外调用；客户端不残留另一城市草案。旧范围policy缺失仍先澄清；无进展同选仍拒绝 |
| A11 已知关闭及TTL组合 | 草案／后续详情发现关闭；另一类别触发补检索；暂停恢复。含5h59→新详情→跨原TTL和有／无替代变体 | 关闭事实自身时效保留，不进入候选；无替代不发布新正式版，有替代正常完成；未知新检索不续期，乱序旧状态不覆盖新事实，accepted_plan保护不回归 |
| A12 API与输入门槛 | 对等调用非流式／SSE；另输入缺日期或北疆未收敛范围 | 两种API业务状态／draft／正式结果一致；SSE实际有中间内容；缺关键信息或范围超限先澄清、不先检索／生成假的单城草案；旧历史与既有automatic冒烟入口可用 |

其中A01、A03、A08、A09至少需要一次浏览器核查，验证内容确实可见、顺序正确、刷新可恢复和草案标签明确。单凭SSE里存在字段或React编译通过不足以证明用户已经看到草案。

A01、A03需保留事件顺序和调用序列证据；A05／A06需有模型违约返回的确定性反例；A08–A12优先使用真实图＋隔离SQLite／ASGI，避免只测helper而漏跨节点行为。

## 6. 通过与不通过的判断标准

**本批通过需要：** 十二场景的核心期望有证据支持，必要浏览器核查完成；既有五轮独立不变量未回归；旧API／历史兼容策略明确；新增限制与未核实项如实表述。允许明确记录环境导致未能执行的非核心真实模型样本，但不能把未做的浏览器／恢复测试写成已通过。

**直接阻断：** 仍先选具体食宿才出路线；流只是假进度而没有提前内容；草案覆盖正式版；用户明确指定被无声忽略；旧选择串到新草案；关闭／TTL／恢复保护回归；为了显示草案关闭完整行程校验。

不要求事前承诺“十秒必出草案”等数字。记录首份有用草案时间、食宿选择后首个有用更新时间、全程耗时、强制决策次数和调用成本，与旧样本／同固定需求做可解释比较。增加草案步骤若显著增加总体调用，也需说明取舍；不能只报告首个进度事件时间来宣称更快。
